# 记忆架构与注入机制

本文档描述当前 `12306-ticket-service` 中多智能体对话记忆的设计、存储方式、注入策略与优化后的分槽方案。

## 1. 设计目标

当前记忆架构要同时解决 4 个问题：

1. 最近几轮对话要能准确承接。
2. 更久之前的重要事实不能因为窗口滑动而永久丢失。
3. 不同专家链路之间不能相互污染。
4. 不同类型问题不能无脑注入全部历史，否则会引入噪声、错误继承和 token 浪费。

因此当前实现采用：

- 短期精确记忆
- 长期结构化摘要记忆
- 会话状态卡桥接
- 结构化业务事实记忆
- 按意图选择的记忆注入策略

## 2. 记忆分层

### 2.1 短期精确记忆

短期记忆保存最近窗口内的真实消息：

- 存储位置：Redis
- Key 前缀：`chat:memory:{memoryId}`
- 过期时间：30 分钟
- 内容：`UserMessage / AiMessage`

它的作用是承接最近几轮真实上下文，适合：

- 购票追问
- 退票确认
- 订单状态延续
- 闲聊中的短轮次连续承接

### 2.2 长期摘要记忆

长期记忆不是原文，而是摘要卡：

- 持久化：MySQL `t_chat_summary`
- 读取缓存：Redis `chat:summary:{memoryId}`
- 过期时间：Redis 缓存 180 分钟

它的作用是承接已经被短期窗口淘汰的旧信息，例如：

- 之前已经确认过的车次、日期、站点
- 已明确的稳定意图
- 未完成动作
- 最近一次关键结论

### 2.3 会话状态卡

会话状态卡不是长期存储，而是追问命中时临时构造的桥接提示，内容包括：

- 上一轮意图
- 上一轮主题
- 结构化事实
- 上一轮结论

它的作用是让系统在追问场景下，不必复读上一轮全文，也能理解：

- 当前问题是否依赖历史
- 当前追问承接的到底是什么主题

### 2.4 结构化业务事实记忆

结构化事实从用户输入中抽取并累积，主要字段包括：

- `trainNumber`
- `orderSn`
- `travelDate`
- `fromStation`
- `toStation`
- `intentHint`

这部分只对 `ACTION / TICKET` 链路注入，不对 `RAG / CHITCHAT` 注入。

## 3. 分槽存储

### 3.1 短期记忆分槽

短期记忆通过 `memoryId` 前缀实现分槽：

- `TICKET:{baseMemoryId}`
- `POLICY:{baseMemoryId}`
- `GENERAL:{baseMemoryId}`

这样不同专家不会共享同一份短期原文消息。

### 3.2 长期记忆分槽

长期记忆现在也已按槽位存储。

实现方式不是改表结构，而是把槽位编码进 `session_id`：

- `POLICY`
- `TICKET`
- `GENERAL`

例如同一个用户同一个会话：

- 票务长期记忆写入 `username + TICKET:sessionId`
- 政策长期记忆写入 `username + POLICY:sessionId`
- 通用长期记忆写入 `username + GENERAL:sessionId`

这样可以避免：

- 政策历史污染票务动作
- 票务订单号污染政策问答
- 通用闲聊干扰业务决策

### 3.3 旧数据兼容

长期记忆分槽后，读取逻辑先查新槽位。

如果新槽位没有摘要，会回退查旧格式摘要；查到后自动迁移写入新槽位，因此旧数据不会立刻失效。

## 4. 长期记忆生成机制

### 4.1 原始问题

如果只根据“消息条数是否减少”判断窗口淘汰，窗口满后很多轮其实已经发生旧消息顶出，但消息总数可能不变，导致长期摘要不能持续更新。

### 4.2 当前做法

现在会保存上一轮消息快照，并和当前窗口做重叠比对：

1. 找出上一轮消息尾部和当前窗口头部的最大重叠。
2. 由此识别真正被淘汰的旧消息。
3. 只把这部分“被淘汰旧消息”交给摘要模型压缩。

这样长期记忆会持续吸收被窗口滑出的历史，而不是依赖长度变化碰运气。

### 4.3 摘要内容格式

长期记忆不再是一段松散自然语言，而是一张结构化摘要卡。

当前摘要提示要求模型尽量输出以下非空字段：

- `稳定意图`
- `已确认事实`
- `待完成动作`
- `最近结论`
- `用户偏好约束`

并且会按槽位给不同提示：

- `POLICY`：优先保留政策主题、适用条件、例外、最近结论
- `TICKET`：优先保留车次、日期、站点、订单号、待完成动作、执行结果
- `GENERAL`：优先保留稳定主题、已确认事实和最近结论

## 5. 注入策略

### 5.1 为什么不能每轮都注入全部历史

如果每轮都把最近 10 轮原文和长期摘要全部塞进 prompt，会带来：

- 上下文噪声
- 意图污染
- 旧事实误继承
- token 成本上涨

因此当前已经从“默认总注入”改成“按场景注入”。

### 5.2 记忆注入策略枚举

当前支持：

- `NONE`
- `RECENT_2`
- `RECENT_4`
- `RECENT_2_WITH_SUMMARY`
- `RECENT_4_WITH_SUMMARY`
- `FULL`
- `FULL_WITH_SUMMARY`

含义：

- `RECENT_2/4`：只注入最近 2 或 4 个用户轮次的原文消息
- `WITH_SUMMARY`：在短期原文前再补一张长期记忆卡
- `NONE`：完全不注入短期原文和长期摘要

### 5.3 当前默认策略

按意图和上下文依赖状态选择：

- `ACTION / TICKET`
  - 独立问题：`RECENT_4`
  - 追问/上下文依赖：`RECENT_4_WITH_SUMMARY`

- `RAG`
  - 独立问题：`NONE`
  - 追问/上下文依赖：`RECENT_2`

- `CHITCHAT`
  - 独立问题：`NONE`
  - 追问/上下文依赖：`RECENT_2`

这意味着：

- 独立政策问答尽量走干净上下文
- 动作/票务链路保留较强承接能力
- 追问场景允许少量原文与必要历史承接

## 6. 典型链路

### 6.1 政策独立问题

用户提问：

`学生票一年可以买几次？`

处理方式：

- 意图路由为 `RAG`
- 若判断为独立问题
- 短期原文不注入
- 长期摘要不注入
- 主要依赖当前问题 + 检索证据

### 6.2 政策追问

用户上一轮问：

`学生票适用于哪些学生？`

当前轮问：

`那一年能买几次？`

处理方式：

- 命中会话桥接
- 注入会话状态卡
- `RAG` 链路仅补最近少量原文
- 不再无脑补票务长期摘要

### 6.3 票务动作追问

用户上一轮问：

`帮我退掉 G123 那张票`

当前轮问：

`全部都退`

处理方式：

- 意图路由为 `ACTION`
- 注入最近 4 轮短期消息
- 若判定依赖历史，再补 `TICKET` 槽长期记忆卡
- 同时注入结构化业务事实

## 7. 当前收益

当前方案的直接收益：

- 降低不同专家之间的记忆污染
- 降低独立 `RAG` 问题的历史噪声
- 让长期记忆持续更新，不再漏掉被窗口顶出的旧消息
- 让长期记忆从自然语言段落变成结构化卡片，更利于模型消费

## 8. 后续可继续优化

后续还可以继续做 3 件事：

1. `POLICY / TICKET / GENERAL` 摘要分别建立独立评测集，量化长期记忆对命中率和污染率的影响。
2. 将会话状态卡也纳入统一注入枚举，形成：
   - `NONE`
   - `STATE_CARD_ONLY`
   - `RECENT_N`
   - `RECENT_N_WITH_SUMMARY`
3. 对长期记忆做“重要事件刷新”，例如：
   - 下单成功
   - 退票成功
   - 订单号确认
   - 政策结论稳定输出

这样长期记忆会更像业务状态机，而不只是被动摘要。
